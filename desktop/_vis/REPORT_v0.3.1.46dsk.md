# v0.3.1.46dsk 交付报告 —— 弹幕侧「快速文本分析」与「弹幕屏蔽总开关」解耦

**日期**：2026-10-10
**触发**：用户报「不开弹幕屏蔽总开关、但开着 fastText 的情况下，依旧应该去屏蔽 fastText
认为该屏蔽的弹幕啊；而且感觉 fastText 似乎没怎么生效」

---

## 一、结论先说

**fastText 在弹幕侧 100% 失效**，原因不是模型坏了，是一行赋值把两条独立通道焊死了：

```js
// desktop/extensions/bilibili-dmfilter.user.js（修复前）
var NEED_TEXT = DM_ON && !!CF.ft_dm;     // DM_ON=false 时恒为 false
```

`askText()` 第一行就是 `if (!NEED_TEXT || ...) return Promise.resolve();` —— 于是**一个文本
请求都没发出去**。而设置页对用户的承诺恰恰是「与上面的『弹幕屏蔽总开关』『评论筛选』
**完全独立**：上面管『谁发的』，这里管『发了什么』」（`web/index.html:658`）。
评论侧 `bilibili-cfilter.user.js:62` 一直是 `var NEED_TEXT = !!CF.ft_cf;`，**没有**这个耦合。

用户的实际配置（读自 `data.db`，只读）正好踩在这个组合上：

| 键 | 值 |
|---|---|
| `ft_on` / `ft_dm` | `1` / `1` ← fastText 开着 |
| `m_dm_on` | `0` ← 弹幕屏蔽总开关关着 |
| `ft_thresh` / `ft_labels` | `70` / `flame,spam,clickbait,yy,neg` |

→ `DM_ON && ft_dm` = `false`，弹幕侧文本通道**静默死亡**。

---

## 二、根因（三层，按影响排序）

### P0 · 门控耦合（决定性，100% 解释症状）

如上。**一行代码，零请求。**

### P1 · XHR 路径从不给文本通道预热（次要，但真实）

播放器走的是 **XHR**（不是 fetch），而 XHR 钩子只 `askFlags`，**没有 `askText`**：

```js
var r = process(new Uint8Array(v));
feedAdd(r.raw);
askFlags(r.hashes, false);      // ← 只有画像，没有文本
this.__msxDmB = r.out;
```

XHR 的 `response` 必须**同步**返回，等不了壳，所以播放器当次那一段永远用不上"这一轮"
的文本判定 —— 但预热出去之后，拖进度条/重看时同一段会再问一次，且「弹幕列表」会靠
`refilter()` 把标记补上。以前唯一的文本数据来源是 `fetchMissing` 自取分段时的预热，
播放器路径本身等于**从没喂过**。

### P2 · 模型对短弹幕有系统性误伤（独立问题，不是这次的 bug）

模型本身是好的（**8231 条/秒**，长文本误伤 **0/2000**），但**训练语料是视频标题/简介/
长评论**（339K 条，`ok` 类 25.2%），**几乎没有短弹幕**。短文本对模型是分布外数据。

补进评测集后（见第四节）在**产品默认档**（T=3.0 / 阈值 70%）上：

| 被误杀的弹幕 | 判定 | 置信度 |
|---|---|---|
| `666` | 阴阳怪气 | **1.000** |
| `笑死我了` | 阴阳怪气 | **1.000** |
| `太强了` | 阴阳怪气 | **1.000** |
| `辛苦了` | 阴阳怪气 | 0.998 |

误伤**全部集中在 3–4 字**（5/173 = 2.9%），5 字以上 0/30。

同时召回也差：短的真垃圾弹幕 38 条只命中 11 条 = **29%**
（`广告狗` / `举报了` / `割韭菜` / `引战狗` 全部 0.000 漏判；而 `滚吧` / `退钱` / `差评`
只有 2 字，被运行期的 `len(t) < 3` 直接跳过）。

> 所以**不能靠"加长度下限"或"调阈值"来救** —— 误伤与真命中在同一个特征空间里，
> 阈值 0.93 也拦不住 1.000 的误判，加长度下限则是同时砍掉误伤和真命中
> （3–4 字真命中 11 条 vs 误伤 5 条）。**唯一正确的修法是重训时补弹幕语料。**

## 三、改了什么

| 文件 | 改动 |
|---|---|
| `extensions/bilibili-dmfilter.user.js` | ① `NEED_TEXT = !!CF.ft_dm`（去掉 `DM_ON &&`）<br>② `process()` 顺带返回本段去重文本 `texts`<br>③ XHR 钩子补 `askText(r.texts, false)`<br>④ 文件头 + `DM_ON` 处注释改写（旧注释"关掉后所有弹幕侧规则一次性失效"正是误解源头） |
| `app.py` | ① `bili_dm_flags()` 增加 `if sget("m_dm_on") == "0": return`（**后端也设防**）<br>② `DEFAULTS["m_dm_on"]` 注释同步<br>③ `APP_VER = "v0.3.1.46dsk"` |
| `web/index.html` | 弹幕总开关 tip 改为「按发送者身份」并注明 fastText 不受影响；黑名单 tip 注明弹幕侧需总开关打开；页脚版本 |
| `_vis/fasttext_demo/eval_bili.py` | ★ 新增 **54 条高频短弹幕的 `ok` 类**（原评测集 `ok` 类只有 5 条 ≤6 字，盲区让精确率虚高） |
| `test_shell.py` | 「文本分析5」断言更新 + 新增「文本解耦1~5」；**168 项 ALL_PASS** |
| `_test_dm_ft_gate.js` | **新增**：node 沙盒行为级回归（7 项） |
| `_verify_dmft_gate.py` | **新增**：打包产物三层验收 |
| `_verify_exe.py` | 加 `MIRRORSORTER_DATA_DIR` 隔离（它原本会改用户的 `ft_labels`） |

**为什么后端也要设防**：`bili_dm_flags()` 自己的注释写着"页面脚本虽然会先自行 gating，
**但不能指望它**"。不设防的话，逆推 300 个哈希 ≈ **3 秒纯 Python CPU**，多候选分支还会把
上千个 mid 塞进**联网**补图队列 —— 那正是把账号打进 -352 风控的源头，也正是这个总开关
存在的理由。

**边界（有意保留）**：总开关**仍然**管着按发送者身份的规则（黑名单 / 抽奖 / 空首页 /
无简介），只放开文本通道。设置页文案已改成与行为一致。

## 四、实测

### 4.1 模型质量（诚实数字）

评测集从 101 → **155 条**（补 54 条短弹幕）后，**产品默认档 T=3.0 / 阈值 70%**：

| 指标 | 补盲区前（旧评测集） | 补盲区后（诚实） |
|---|---|---|
| 精确率 | 100.0% | **94.3%** |
| 召回率 | 93.0% | 93.0% |
| F1 | 96.4% | **93.6%** |
| 误杀数 | 0 | **4** |

> 旧评测集的 100% 精度是**盲区造成的虚高**，不是模型真的那么准。

漏杀 5 条：`画面真棒，棒到我电脑冒烟了`(yy, 0.046)、`这更新真快，快到又崩了`(yy, 0.187)、
`低价代充，详情见简介`(spam, 0.558)、`看我主页，有需要的私聊`(spam, 0.133)、
`掉帧严重，卡成ppt了`(neg, 0.408)。

### 4.2 打包产物验收（`_verify_dmft_gate.py`，三层全过）

```
【1】静态  打包内 userscript 与源码字节一致 / NEED_TEXT 已解耦 / XHR 已补预热
【2】行为  把 exe 里抽出来的那份 userscript 跑 node 沙盒 → ALL_PASS (7 checks)
【3】运行期 隔离库 + 隔离端口，复刻用户配置(m_dm_on=0 + ft_on=1 + ft_dm=1):
           /api/textfilter kind=dm → {"ok":true,"on":true,"why":["阴阳怪气","","阴阳怪气"]}
           /api/bili/dmflags       → {"flags":{},"pending":[]}   ← 身份规则仍被掐死
           m_dm_on=1 后            → pending=["aabbccdd"]        ← 恢复入队
```

### 4.3 行为回归有判别力（关键）

把 `NEED_TEXT` 改回旧写法再跑同一份沙盒：

```
FAIL  T1 总开关关 + fastText 开 → 弹幕侧照发文本请求
      <<< 实际 textfilter 请求数=0
FAIL  T5 总开关关 + 黑名单表注入 → ...  <<< textfilter=0
RESULT: FAIL(2)
```

→ 测试**确实抓得住**这个 bug（静态断言抓不住：出错的是一行完全合法的赋值）。

## 五、遗留 / 建议（需要用户决策）

1. **★ 重训模型，补弹幕语料（首要）**
   当前 `ok` 类以标题/简介为主，短弹幕是分布外数据。建议在 `build_corpus.py` 里
   加一路"高频短弹幕"来源（`666`/`前排`/`泪目`/`太强了` 这类），并把
   `_vis/fasttext_demo/eval_bili.py` 新增的 54 条短弹幕纳入验收门槛。
   目标：把 3–4 字的误伤从 2.9% 压到 <0.5%，同时把短垃圾弹幕召回从 29% 提上去。

2. **可选的兜底：高频正常弹幕白名单**
   弹幕重复率极高，一份 top-N 常见正常弹幕白名单能消掉绝大部分**用户看得见**的误伤，
   成本近乎为零。但这属于产品判断（要维护一份词表），**未擅自实施**。

3. **`build_corpus.py:MINLEN = 2` 与 `app.py:ft_scan` 的 `len(t) < 3` 不一致**
   训练收了 2 字样本，运行期却跳过。实测 2 字文本 `急了`/`麻了`/`呵呵` 命中 1.000（该拦），
   但 `太强` 0.998（不该拦）—— 放与不放各有得失，**未擅自改动**，交由决策。

4. **默认标签里 `neg` 误伤偏多**
   用户当前勾了全部 5 个标签（含 `neg`）。设置页原本就写着"默认不勾『负面情绪』——
   正常吐槽也会被它命中"。本次实测的 4 条误杀全是 `yy`，`neg` 未造成误伤，故未改动。

---

## 六、一句话总结

**根因是一行 `DM_ON &&` 把"谁发的"和"说了什么"焊死了，改掉之后 fastText 在弹幕侧立刻生效
（`/api/textfilter` kind=dm 返回 `["阴阳怪气","","阴阳怪气"]`）。**
顺带发现模型对短弹幕有系统性误伤，根子在训练语料缺弹幕 —— 这个必须靠重训解决，
并且我把评测集的盲区补上了，免得下次还拿虚高的指标自证。
