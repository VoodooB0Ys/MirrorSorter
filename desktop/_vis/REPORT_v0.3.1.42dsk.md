## 1. 问题：为什么"你的机器不黑、用户的机器黑"

**不是配置错，也不是 v0.3.1.36dsk 修过的那个 bug**（那次是 `float_of` 名字拼错导致
`AttributeError` 被 `except` 吞掉 → **必黑**且关窗仍出声）。这次是**概率性**的残余竞态：

- 悬浮窗的实现是"用 `Control.Parent` 把**同一个** WebView2 控件从主窗体搬进悬浮窗体"
  （页面不重载）。Chromium 用 DirectComposition 呈现内容，而"宿主窗口编排变化"的瞬间
  合成层会被打断 → 画面整块停在同一色（`#0f1115`）且**不自愈**。
- 旧补救 `_retext_later` 在 **0.35 / 0.9 / 1.6 秒**三个**写死**的时间点各补一次
  「隐藏→显示→置顶」，**既不校验是否真出图、也不重试**。
  ⇒ 用户机（WebView2 冷启动慢 / GPU 驱动初始化慢 / 多屏混合 DPI / 混合显卡）合成层重建
  晚于 1.6s，三次补救全部落空 → **黑屏永久留下**；开发机快，1.6s 内早就好了 → 看着"没问题"。

这就是同一份代码在两台机器上表现相反的全部原因。

## 2. 修法：把"固定三次"换成**校验 + 重试**的看门狗

| | 旧 | 新（v0.3.1.42dsk） |
|---|---|---|
| 补呈现时刻 | 0.35 / 0.9 / 1.6s（写死） | 0.25 / 0.6 / 1.1 / 1.8 / 2.8 / 4.0 / 5.5 / 7.0s（递进） |
| 是否校验 | **否** | **是** —— 每次补完抓屏判定是否真出图 |
| 判定依据 | — | **"是否整块同一个颜色"**（不是"是不是黑"） |
| 还黑怎么办 | 撒手 | 继续补，并**逐级加重手段**，直到出图或到 8s 上限 |
| 快机器代价 | 3 次 toggle | **1 次**（第一次校验就健康 → 立刻收工） |

### 为什么判"平色"而不是判"黑"
视频层被提升为 DComp 独立平面时，GDI 本来就抓不到那块（会读到黑），但页面其余部分
（播放器控件 / 页面底色 / 弹幕层）是能抓到的。⇒ 只有**整块完全同一个颜色**才是
"根本没呈现"的特征；单看黑会把正常的播放页误判成坏，然后无谓地反复 toggle。
（这一条有真窗口实测兜底，见第 4 节。）

### 手段阶梯（全部**不重载页面**，页面状态原样保留）
1. **轻**：隐藏 → 显示 → 置顶（与旧实现一致）
2. **中**：再加一次强制重绘（`Invalidate(True)` + `Update()`）
3. **重**：从父容器**摘下再挂回**（几何原样还原）—— 逼宿主重走一遍编排

## 3. 兼容性：把"宿主编排变化"的事件全接上

原来只在**两处**触发补呈现（迁进悬浮窗、进全屏）。现在补齐了会打断合成层的其余入口：

| 触发 | 位置 |
|---|---|
| 迁进悬浮窗 | `shell_pages.send_to_window`（原有） |
| 进网页全屏 | `shell_pages.set_fullscreen`（原有） |
| **悬浮窗被激活**（从别的应用切回来） | `shell_float._wire_repaint` → `form.Activated` |
| **悬浮窗缩放 / 最大化 / 还原** | `form.Resize`（最小化态跳过；尾部去抖 450ms） |
| **悬浮窗拖动 / 换显示器** | `form.LocationChanged`（尾部去抖 450ms） |
| **DPI 变化** | `form.DpiChangedAfterParent` + `form.DpiChanged` |
| **从悬浮窗塞回标签页** | `app_window.window_dock` → `pages.represent(tid, "undock")` |

去抖的意义：拖动/缩放过程中事件很密，只在**动完了**补一次，不干扰手感。
看门狗在控件被隐藏 / 换掉 / 销毁时会**立即取消**（否则它会把刚藏起来的控件又 toggle 出来）。

### 排障与诊断
- **A/B 开关** `MSX_NO_REPRESENT=1` → 退回旧行为（固定三次、不校验），用来确认新旧差异。
- **机器环境落盘**：启动时把和机器强相关的字段写进 `shell_debug.log`
  （OS / 系统 DPI / 显示器数 / **WebView2 内核版本** / 浏览器参数 / 是否 MSX_BASIC）。
  悬浮窗黑屏这类问题几乎全是机器差异 —— 有了这一行，下次用户报修第一句就能拿到关键字段，
  不用再靠猜。

### 探针覆盖的关键行为（`_verify_represent.py`）
- 看门狗排程/旧行为排程常量齐备
- 手段阶梯 `[1,1,2,2,3,3,3]` 正确

- **还黑就继续补**：第 3 次才出图 → 补 3 次后停
- **一直黑补满排程**（不再像旧实现那样三次就撒手）
- **重手段真的生效**：排到第 3 级时确实把控件从父容器摘下再挂回
- **检测判不了（None）不误判为健康**，继续补
- `MSX_NO_REPRESENT=1` 退回旧行为（固定三次、不校验）
- **取消生效**：控件隐藏/换掉后看门狗立即停

- **真 GUI 判色**：整块平色 → `True`（判"没出图"）；画面有内容 → `False`（判"健康"）；

## 5. 顺带修的一处测试脆弱性
`test_shell.py` 原来硬性要求 `dist\*安装包*.exe` 存在 —— 那是 NSIS 产物，全新检出 / 清理后
没打包就会判 FAIL（本次清理删掉 `dist/` 后就撞上了）。改成：
- 有 `dist/*.exe` → 检 PyInstaller onefile exe（必检）
- 有 `*安装包*.exe` → 检安装包；没有 → **SKIP**（语义是"打好的包是对的"，不是"必须已经打过包"）
