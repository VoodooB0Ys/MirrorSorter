# 内置 0.5B 小模型做数据筛选 —— 可行性评估

> ⚠️ **本版（v1）的核心结论已被推翻，请阅读 `REPORT_小模型筛选评估_v2.md`。**
> v1 用「功能没开」时的账单（¥1.52）去论证「功能开了也不贵」，是无效推论。
> 实测三通道全开 AI 为 **¥245 ~ ¥1,536/月**，且 0.5B decoder 的 CPU 吞吐（0.83~3.3 条/秒）
> 根本接不住弹幕的突发需求（~1,000 条/秒）。**v1 仅保留作过程记录。**

> 评估对象：信息筛选 / 评论筛选 / 弹幕筛选 三条链路
> 评估维度：运行速度 · 性能占用 · 效率 · 效果
> 评估日期：2026-10-10
> 状态：**纯评估，未改动任何代码**
> 基线版本：v0.3.1.42dsk

## 0. 结论摘要（先看这段）

| # | 结论 | 依据 |
|---|---|---|
| 1 | **「API 太花钱」这个前提不成立** | 全历史 31 天实测 API 总花费 **¥1.52**；最近 10 天合计 **¥0.0019**。按默认设置（只评热度前 120 条）折算约 **¥1.1/月** |
| 2 | 真正的问题是**「机械筛选太弱」= 效果问题**，不是成本问题 | 机械侧是固定词表 + 正则，无上下文理解，词表覆盖外全漏 |
| 3 | **三条链路里只有「信息筛选」适合上模型** | 它是语义分类；评论/弹幕是**账号身份关联**，不是语义分类 |
| 4 | **不该用 0.5B decoder，该用 ~100M encoder 分类器** | decoder 逐条 300ms（强机）～3s（弱机）；encoder 批处理 3~8ms/条 |
| 5 | **弹幕链路基本不可能上模型** | 跑在渲染进程内的用户脚本里，必须同步亚毫秒；且全片弹幕量 3000~8000 条 |
| 6 | **最大障碍不是模型，是没有标注数据** | `items` 表 24511 条，`score_json` 字段**全为空**，当前零可用训练样本 |
| 7 | 若坚持做，代价是**安装包 +400~500MB**（当前 exe 21MB） | Q4_K_M ≈ 380MB / Q5_K_M ≈ 480MB |

**一句话**：现在不该做这件事。省钱不是理由（本来就不贵），效果上只有信息筛选一条链路有真实增益空间，而且正确形态是「小 encoder + 蒸馏」，不是「内置一个 0.5B 通用小模型」。**但有一个零成本的准备工作应该立刻做**（见 §7 第 0 步）。

单价按设置 `price_in=1.0` / `price_out=2.0` ¥每百万 token。

### 1.2 关键推论

- **单次调用均值**：输入 1,428 tokens / 输出 1,656 tokens → **¥0.00474/次**
- **单条成本**（`ai_batch=15`，每批 15 条）→ **约 ¥0.00032/条（0.032 分）**
- **默认档**（`ai_full_scan=0`，每天只评热度前 120 条）→ **¥0.038/天 ≈ ¥1.1/月**
- **假设开全量扫**（按实测日均抓回 ~4,900 条）→ **¥1.57/天 ≈ ¥47/月**
- **最重的一天**（8-28，124 次调用）也只花了 **¥0.83**

### 1.3 结论

> 用户感知的「API 太花钱」，与实际账单差了一个数量级。当前默认档下，API 一年的花费不到一杯咖啡。
>
> **所以「换小模型来省钱」在算术上不成立**——省下的是 ¥1~47/月，付出的是 400MB 安装包、一套训练工程、以及每次筛选的延迟。

### 1.4 顺带发现：token 成本的真实构成

`SCORER_SKILL` 要求每条内容输出 **8 项**：`flame` / `spam` / `interest` / `density` / `emo` / `facts` / `topic` / `reason`。

其中 `reason` 是**生成式**的「一句 20-40 字口语化推荐理由」——按输出均值 1,656 tokens / 15 条 ≈ 110 tokens/条，`reason` 独占约 30~60 tokens，**占单条输出的 1/3 以上**。而输出单价是输入的 2 倍。

**这是目前 token 成本最大的单点**，也是最容易优化的一处：把 `reason` 拆成独立可选调用（只在用户真要「推荐理由」时才生成），可省下约 20~25% 总花费。**但这属于省钱优化，不是本评估的命题**——因为省的钱本来就很少。

## 2. 三条链路的本质辨析（决定小模型有没有用武之地）

这是本次评估最重要的一节。三条链路看起来都是「筛选」，但**数学本质完全不同**。

### 2.1 信息筛选 —— 真·语义分类 ✅ 有增益空间

**现状实现**：

| 层 | 手段 | 位置 |
|---|---|---|
| 规则层（零 token） | `_emotion_filter`：感叹号/问号轰炸（≥3）、叠词 4 连、`FLAME_SLURS` 引战黑话表、`CLICKBAIT_KWS` 标题党词表、`CLICKBAIT_RE` 句式正则 | `app.py:8496-8514` |
| 规则层 | `_ad_bad`：查简介，`AD_HARD` 硬标记任一命中 / `AD_SOFT` ≥2 命中 | `app.py:8517-8525` |
| 规则层 | 播放量窗口、时长窗口、去重指纹、冷却、拉黑名单 | 抓取侧 |
| API 层 | `SCORER_SKILL` 8 维打分（含 `reason` 生成） | `app.py:5295-5330` |

**机械侧的弱点（真实存在）**：
- 词表是**穷举式**的。`FLAME_SLURS` 收了 34 个词，`CLICKBAIT_KWS` 收了 50 个词——但「开团」因为游戏区正常用法被**刻意排除**，这类边界词是词表法的死穴。
- 无上下文。「这游戏真是把我气笑了」不含任何黑话词，但它是引战氛围；「XX 都看不下去了」被 `CLICKBAIT_RE` 抓到，但正常吐槽也长这样。
- 无跨语言/变形对抗。拼音、谐音、空格插字、emoji 替代，词表全漏。
- `spam` 的判据（AI 生成图片配空洞文案、标题说 A 内容讲 B）**完全无法用规则表达**。

**这一条是三条链路里唯一「语义分类」问题**，也是唯一值得上模型的地方。

### 2.2 评论筛选 —— 账号身份关联 ❌ 无增益

**现状实现**（`bilibili-cfilter.user.js:335-353`，`keep()` 函数）：

```
保留判定 = 昵称不在黑名单
       且 简介非空（可选）
       且 mid 不在「抽奖号」标记表
       且 mid 不在「空首页」标记表
       且 等级 > 阈值（可选）
```

全部是 **O(1) 查表**，数据由壳端 `/api/bili/flags` 提供（实测 3~45ms，本地只读缓存）。

**为什么不需要模型**：
- 判据是「这个**账号**是不是营销号/抽奖号/僵尸号」，依据是**账号侧证据**（简介、首页动态、等级、是否在用户黑名单）——**不是评论文本内容**。
- 这是**身份关联**问题，不是**语义分类**问题。0.5B 模型读一条评论文本，无法知道发帖人简介里有没有「加微信」。
- 而且现有解已经是正解：O(1)、亚毫秒、零延迟、可解释（用户能看到「为什么被筛」标签）。
- 硬要上模型只会**更慢更差**：200 条评论 × 300ms = 60s，用户翻评论页会卡死。

### 2.3 弹幕筛选 —— 身份关联 + 渲染进程内实时 ❌❌ 双重不可能

**现状实现**（`bilibili-dmfilter.user.js`）：
- `document-start` 劫持 `api.bilibili.com/x/v2/dm/.../seg.so`（protobuf 二进制）**响应体**
- 就地摘掉不该显示的弹幕条目，保留的按**原始字节**原样回填
- 判据（`blkWhy()`，第 262-280 行）：黑名单哈希 / 无简介 / 抽奖 / 空首页 / 等级低
- 弹幕接口**只给 `midHash`**（= crc32(十进制 mid) 的 8 位 hex），**没有昵称、没有等级、没有简介**
- 其余画像靠壳端 CRC32 逆推 mid 后查缓存

**为什么不可能上模型**：

| 障碍 | 具体数字 |
|---|---|
| **运行环境** | 用户脚本跑在 B 站页面的**渲染进程**里，纯 JS、**同步**、必须亚毫秒返回。WebGPU/WebNN 加载模型需 50~500ms，每批推理 5~20ms——**首次加载就把弹幕卡住** |
| **数据量** | 实测单段 protobuf：半段 52KB / 完整段 98KB。一个 10 分钟视频全片弹幕量级 **3,000~8,000 条** |
| **时间预算** | 即使 encoder 批处理 5ms/条，5,000 条也要 **25 秒**；decoder 300ms/条则要 **25 分钟**。而弹幕必须在 `seg.so` 响应返回的那一刻同步过滤完 |
| **判据性质** | 和评论一样，是**身份关联**（黑名单/抽奖号/空首页/等级），不是内容语义 |
| **可用字段** | 接口只给 `midHash`，账号侧证据全在壳端。模型拿不到它需要的输入 |

**唯一理论上的缝隙**：如果要做「弹幕**内容**语义筛选」（刷屏/无意义/引战），文本是有的（`DanmakuElem.7 = content`）。但走壳端异步意味着「先显示再隐藏」的闪现，走渲染进程内则被上面的时间预算否掉。

## 3. 0.5B 小模型的真实性能基准

### 3.1 Qwen3-0.6B —— 官方 benchmark

来源：Qwen 官方效率评估文档（H20 96GB GPU，SGLang，batch=1，生成 2048 tokens）

| 输入长度 | 量化 | 速度 (tokens/s) |
|---|---|---:|
| 1 | BF16 | 1,414.17 |
| 1 | FP8 | 1,458.03 |
| 1 | GPTQ-Int8 | 1,344.92 |
| 6,144 | BF16 | 1,426.46 |
| 30,720 | BF16 | 3,577.42 |

Transformers 后端（无 SGLang 优化，更接近本地部署实感）：

| 输入长度 | 量化 | 速度 (tokens/s) | 显存 (MB) |
|---|---|---:|---:|
| 1 | BF16 | 158.57 | 1,394 |
| 1 | GPTQ-Int8 | 126.56 | **986** |
| 30,720 | BF16 | 175.93 | 4,755 |
| 30,720 | GPTQ-Int8 | 345.71 | 4,347 |

> ⚠️ 以上全部是 **GPU 数据**。本产品是**纯 CPU 分发**（不依赖用户有独显），官方表格里没有 CPU 数据。

### 3.2 Qwen2.5-0.5B 微调做中文文本分类 —— CPU 实测

来源：中文实践文章（llama.cpp，CPU only，Q5_K_M）

| 指标 | 数值 |
|---|---|
| 基线准确率（未微调） | **10.59%**（召回 15.34%） |
| 微调后准确率 | **95.61%**（召回 96.18%） |
| 训练数据 | **2 万条**（Qwen2.5-32B 合成 + 人工标注补 `other` 类） |
| 部署方式 | llama.cpp，GGUF Q5_K_M，纯 CPU |
| **单条延迟** | **~300ms / request** |
| 关键优化 | ① prompt 改造为**只输出 1 个 token**；② 启用 prefix cache 复用系统提示词 KV |

**该实验的三个关键结论**（对本次评估极有价值）：
1. **基线几乎不可用**（10.59% ≈ 随机猜）。0.5B 通用模型**不做微调直接拿来分类是没用的**。
2. **必须微调，且必须要有标注数据**——2 万条，其中相当部分需人工标注。
3. **0.5B 对训练技巧极度敏感**（loss 计算位置、warmup、蒸馏比例），换到 3B 上这些技巧**全部无增益**。小模型是「调出来」的，不是「下载来」的。

### 3.3 磁盘与内存占用推算

| 形态 | 磁盘 | 运行时 RAM | 说明 |
|---|---:|---:|---|
| Qwen3-0.6B Q4_K_M GGUF | ~380 MB | ~600~900 MB | 含 KV cache |
| Qwen3-0.6B Q5_K_M GGUF | ~480 MB | ~700~1,000 MB | 实践中效果优于 Q8_0 |
| 中文 encoder（RoBERTa-base/MacBERT ~102M）int8 ONNX | **~100~120 MB** | ~200~300 MB | **推荐形态** |

对照当前分发包：`洞鉴虚明v0.3.1.42dsk.exe` = **21.3 MB**。
→ 加一个 0.5B Q4 模型，**exe 体积翻约 19 倍**；即使走 NSIS 压缩安装包，也是从「几十 MB」跳到「几百 MB」。

### 3.4 一个必须说清楚的不确定性

§3.2 的 **300ms/条是在一台正常配置机器上测的**。本产品的实际用户环境（见 v0.3.1.42dsk 的悬浮窗黑屏排查）包含**老旧/低配机器**。

在弱 CPU（老 4 核、无 AVX-512）上，prefill 速度可能只有强机的 1/5~1/10：
- 单条 300ms → **1.5~3s**
- 5,000 条全量 → **2~4 小时**

**这条不确定性足以单独否掉「全量扫」方案**，而「热度前 120 条」档下 120 × 3s = 6 分钟，也仍然是用户可感知的卡顿。

## 5. 成本对照总账

| 方案 | 一次性代价 | 持续代价 | 月成本 | 效果增益 |
|---|---|---|---|---|
| **维持现状（API 默认档）** | 0 | 0 | **¥1.1/月** | 基线 |
| 维持现状 + 开全量扫 | 0 | 0 | ¥47/月 | 覆盖率↑ |
| 内置 0.5B decoder（信息筛选） | 训练工程 + 标注 2 万条；安装包 +380MB | 每次筛选 300ms~3s/条；RAM +900MB | ¥0 直接成本，但**机器成本/体验成本远超省下的钱** | 未知（可能不如 API） |
| 内置 encoder（信息筛选，蒸馏） | 标注/蒸馏数据；安装包 +100MB | 3~8ms/条 | 接近 ¥0 | 可能接近 API |

**核心算术**：为了省下 ¥1.1~47/月，付出 380MB 安装包 + 一套训练/标注流水线 + 明显延迟 —— **投入产出严重不成比例**。

**唯一可能成立的正当理由**：用户环境**完全离线**（无 API 可用）。但这与「API 太花钱」是两回事，需要用户明确。

## 6. 如果一定要做，正确的做法是什么

**不是**「内置一个 0.5B 通用小模型替换三条链路」，而是：

### 6.1 拆开 `SCORER_SKILL` 的「分类头」与「生成头」

| 输出项 | 性质 | 可否本地化 |
|---|---|---|
| `flame` `spam` `density` `emo` `facts` | **分类/回归**，输出极短 | ✅ 可本地化（encoder） |
| `interest` | 需要**用户画像**参与 | ⚠️ 需把画像编码进输入，可行但难 |
| `topic` | 生成式短标签 | ⚠️ 可退化为固定类目分类 |
| `reason` | **自由生成** | ❌ 必须留 API |

→ 本地只接**分类头**，`topic`/`reason` 仍走 API。这样本地模型是「预筛 + 提纯」，API 调用量下降，但**不是取代**。

### 6.2 形态必须是 encoder，不是 0.5B decoder

- 中文 RoBERTa / MacBERT-base（~102M），int8 ONNX，**~100MB**
- CPU 批处理 **3~8ms/条**，比 0.5B decoder 快 **40~100 倍**
- 输出是**分类 logits**，天然适配 `flame`/`spam`/`density` 这类 0-10 打分
- 代价：**必须微调**，且**必须是中文单语**（参考 Bielik Guard 0.5B 是波兰语专用，跨语言不可迁移）

### 6.3 部署位置：壳端（127.0.0.1），不进渲染进程

- 壳是 Python，可跑 ONNX Runtime，不污染 B 站页面
- 复用现有 `/api/bili/flags` 那套「异步问壳 + 超时兜底」的模式
- **评论/弹幕侧仍走身份关联机械解**，模型只服务信息筛选

### 6.4 明确不要做的事

| ❌ 不要做 | 原因 |
|---|---|
| 在渲染进程内加载模型 | 用户脚本必须同步亚毫秒；加载 50~500ms 直接卡住页面 |
| 用 0.5B decoder 逐条判评论/弹幕 | 300ms~3s/条 × 数百到数千条，完全不可接受 |
| 不做微调直接用 0.5B 分类 | 实测基线 10.59%，等于随机 |
| 为了省钱做这件事 | 省 ¥1.1~47/月，不成比例 |
| 一次替换三条链路 | 评论/弹幕本质不是语义分类，替换必然退化 |

## 7. 建议的下一步（都不需要现在做）

### 第 0 步 —— **零成本，建议立刻做**（唯一真正的「现在就做」）

**把 AI 评分打开，让它跑起来，并把结果落库。**

理由：
- 当前 `items` 表 24,511 条，`score_json` **全为空**——**没有任何可用作蒸馏标签的数据**
- 这是整条技术路线**最大的、也是唯一的硬阻塞**
- 按实测单价，跑满一年也就 ¥13（默认档）
- 有了历史评分数据，未来无论走 encoder 蒸馏还是走规则挖掘，都有了地基

顺带把 `SCORER_SKILL` 的输出结构改成「分类头可独立调用」，为将来的本地化预留接口。

### 第 1 步 —— 先压榨机械规则的上限（免费）

在引入模型之前，先用**已有 API 评分数据**反查机械规则的漏网与误伤：
- 哪些 `flame≥8` 的内容**不含任何** `FLAME_SLURS` 词？→ 补词表
- 哪些被 `CLICKBAIT_RE` 命中的内容实际 `spam≤3`？→ 修正则
- 这一步可能就能吃掉大部分「机械筛选太弱」的痛点，**零模型成本**

### 第 2 步 —— 只有当第 1 步触顶，才考虑 encoder 蒸馏

条件：
- 已积累 ≥1 万条带 API 评分的样本
- 第 1 步的规则优化已到边际收益递减
- 用户明确接受安装包从 21MB 涨到 ~120MB

### 第 3 步 —— 明确放弃的方向

- 弹幕内容语义筛选（渲染进程内不可行）
- 评论语义筛选（问题本质是身份关联）
