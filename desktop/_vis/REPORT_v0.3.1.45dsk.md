# 洞鉴虚明 v0.3.1.45dsk —— 删除弹幕等级筛选 + 画像补图链路止损

交付物：`desktop\dist\洞鉴虚明v0.3.1.45dsk.exe`（**78,365,513 字节 = 74.7 MB**，2026/10/10 16:14）

用户原话：
> 我们软件现在新增了fasttext内置模型，而且还有机械筛选（小于n级的评论、弹幕屏蔽），
> 但是现在这些筛选非常的慢，经常一两分钟了筛选不了三四条弹幕和评论，快速解决一下这个问题
>
> （追问后）等级筛选、fasttext筛选不是本地进行的吗，为什么会被风控？
>
> （决策）弹幕等级筛选功能删掉吧，其他的照常进行，并且进行优化速度

---

## 0. 一句话结论

**三条筛选链路里只有「弹幕等级筛选」必须联网。** fastText 与评论等级筛选都在本地，
实测分别是 10,368 条/秒和 3.5ms —— 它们从来不会触发风控，也从来不是瓶颈。
弹幕等级筛选则要「本地逆推哈希 → 候选 mid → 联网查账号资料」，一个 8 位哈希平均撞出
**6.17 个候选（最大 36）**，一个播放页上千次 B站请求，直接把账号打进 **-352 风控**；
而风控期间请求 100% 失败，旧实现又把失败的 mid **直接丢弃** —— 于是"永远筛不出来"。

处置：**弹幕侧等级筛选删除**（等级只保留评论侧），并给画像补图链路补上
**全请求过闸门 + 取消突发 + 风控硬退避 + 失败重入队**。

## 1. 三条链路的本地 / 联网边界（用户问题的正面回答）

| 链路 | 是否本地 | 实测 |
|---|---|---|
| 文本 fastText | **纯本地**（`ftrt` 纯 stdlib） | 加载 0.032s，**10,368 条/秒**（0.096ms/条）；`/api/textfilter` 500 条 = 44ms |
| 评论等级筛选 | **纯本地** | B站评论接口响应自带 `member.level_info.current_level`，`cfilter.keep()` 直接比 → 零网络 |
| **弹幕等级筛选** | ★ **必须联网** | 弹幕 protobuf 只给 8 位 `midHash`（=crc32(mid)），**不带等级** |

弹幕判等级只有一条路：本地逆推 crc32 → 候选 mid → **联网打 `x/space/wbi/acc/info`**。
所以风控只可能出在这条路上。

## 2. 证据：为什么会被风控

### 2.1 候选爆炸 + 双请求

- `crc32_reverse_fast` 本身很快（实测 **10.5ms/哈希**，纯本地）。
- 但库里 200 行实测：**ncand 平均 6.17、最大 36、多候选占 89%**。
- 且 `bili_author_meta` 的设计是「一份缓存 = 简介 + 动态一起取」→ **每个 mid 打 2 个接口**
  （`acc/info` + `polymer/web-dynamic/feed/space`）。一个 300 弹幕的播放页 ≈ 1800 候选 ≈ 3600 次请求。

### 2.2 档位 A/B（隔离库副本 + 真实接口，各 50 个候选 mid）

| 档位 | 并发 | 标称速率 | -352 风控占比 |
|---|---|---|---|
| 0 | 1 | 1.7 账号/秒 | **92%** |
| 1 | 3 | 4.0 | 96% |
| 2（默认） | 6 | 7.0 | **100%** |
| 3 | 12 | 14.0 | 100% |

- 连**并发 1、1.7 账号/秒都 92%** → **不是速率太快触发的，是账号/IP 已经被标记**，
  一旦进去就是"全有全无"（隔 1 分钟单发 1 个请求仍然 -352）。
- 但**顺序单发 16 次（6.7 请求/秒）实测 0%** → 诱因是**突发 + 并发**，不是稳态速率。
- ★ 旧实现的令牌桶只给"账号"发令牌，而一个账号要打 **2 次**接口，
  标称 7/s 实际是 **14 请求/秒**，且**动态那次完全不受闸门管**。

### 2.3 真正的放大器：-352 之后 mid 被直接丢弃

- `bili_author_meta` 里 `acc/info` 非 0 非 -404 → **`return None`，不写任何缓存**（原设计防误杀）。
- `_am_warm_worker` 失败后只 `_am_warm_seen.discard(m)`，**不重新入队**；队列一空线程就退出。
- 实测：73 个候选入队 → **7.5 秒排空 → 只落库 26 个**（2 画像 + 24 不存在），
  剩下 47 个再也不会被重试；端到端模拟播放页轮询 60 秒，**只筛出 2 条**。
- 附带：`_AUTHOR_WARM_CAP = 60`，73 个候选当场就丢 13 个。

## 3. 改动清单

### 3.1 删除弹幕等级筛选

- `extensions/bilibili-dmfilter.user.js`
  - 删掉 `LV`、`flagsURL` 的 `&lvl=`、`blkWhy` 里的「等级低」分支
  - `NEED_FLAGS = MYSTERY || LOT || EMPTY` → **默认配置下弹幕侧零画像请求**
  - 文件头补上"为什么弹幕侧没有等级筛选"
- `app.py`
  - `_am_bad()` 去掉 `lvl` 参数与等级条件
  - `_dm_flag_of()` 去掉 `level` 字段
  - `bili_dm_flags()` 去掉 `lvl` 参数
  - `/api/bili/dmflags` 不再解析 `?lvl=`（旧注入脚本带它也忽略）
- `web/index.html` 文案：等级明确写「**只作用于评论**」+ 说明为什么弹幕侧没有
- **保留** `cf_min_level` 与 `__MSX_CF__.lvl` —— `bilibili-cfilter` / `bilibili-ownui`
  的评论侧仍在用（测试里专门锁了这条，防止连坐删掉）

### 3.2 删掉 `_mig_am_level27` 一次性迁移

它把几百行画像的 `nodyn` 置 NULL 触发全量重取，正是"一打开页面就发几百次 B站请求"的推手。
等级既然不再被任何规则使用，这个迁移只花钱不办事。`level` 列保留（不再读写），免得为删列做表重建。

### 3.3 画像补图链路止损（速度优化的核心）

| 项 | 旧 | 新 |
|---|---|---|
| 速率口径 | 每**账号** 1 个令牌（实际 2 请求/账号，动态那次不限速） | **B站请求/秒**，两个请求各取一个令牌 |
| 档位表 | 0:1.7 / 1:4 / 2:7 / 3:14 账号每秒 | 0:3.3 / 1:6 / 2:8 / 3:14 **请求**每秒 |
| 突发额度 | `burst = 并发数`（入队瞬间 6 线程同打同一 cookie） | **`burst = 1`**，不允许并发突发 |
| 撞 -352 | 连续 3 次才砍半，5 分钟后满速恢复 | **立刻暂停整个队列**，指数退避 60→180→600→1800s |
| 退避期间 | 继续按低速率撞击 | worker **原地等待，不 pop 队列**（条目留在队里，恢复后继续） |
| 失败处理 | 只从 `seen` 删掉，**永不重试** | `_am_tries`/`_am_retry` 两张表 + 常驻 `_am_retry_ticker` 退避重排 |
| 队列上限 | 400 / 单次认领 60 | **3000 / 400** |
| 规则全关时 | 仍逆推 300 个哈希（≈3 秒纯 CPU）并把候选塞进联网队列 | **后端直接返回**，不逆推、不入队 |
| 前端回问窗口 | `40 × 1.5s` = 60 秒 | `300 × 2s` ≈ **10 分钟**；评论侧新增 `retryPending()` |

## 5. 本轮踩到的两个坑

1. **重试计数与到期时间必须分开存。**
   一开始把 `_am_retry[m] = (次数, 到期)`，而"重入队"要 `del _am_retry[m]`
   → 次数被一起清零，退避永远回到第 1 档。实测 8 个 mid 在 14 秒里被打了 **192 次**，
   封顶形同虚设。拆成 `_am_tries`（计数）+ `_am_retry`（到期时间）才对。
2. **改完 `app.py` 再打包。**
   本轮先起了打包、又在打包途中改了 `app.py`，产物里会是旧代码 —— 只能重打一遍。
   和既有的"改完 `web/` 必须重打包"是同一条规矩（PyInstaller 在 Analysis 阶段采集）。

## 6. 已知边界

- 弹幕侧的「无简介 / 抽奖 / 空首页」三项**仍然需要联网**（默认全关）。
  它们的候选爆炸问题没有消失，只是不再由等级规则强制触发。
  在默认配置下这三项关着 → 弹幕侧纯本地（黑名单查表 + fastText），瞬时生效。
- 用户的账号在本次诊断中已被打进 -352 风控（B站侧通常几十分钟到几小时自动解除）。
  解除前，弹幕侧那三项账号级规则仍然拿不到画像；新代码会在风控期间安静退避、
  恢复后自动补图，不再像旧版那样把队列打光。
- 「哈希对上多个账号时」默认仍是「全命中才拦」（零误杀）。它叠加请求失败率后命中率偏低，
  属于口径问题而非性能问题，本轮未改。
