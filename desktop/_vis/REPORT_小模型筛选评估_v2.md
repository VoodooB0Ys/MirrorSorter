## 1. 真实成本：三通道全开 AI 到底多贵

### 1.1 计费参数（已核对）

| 项 | 值 | 来源 |
|---|---|---|
| `ai_base` | `https://api.deepseek.com/v1` | 生产库 settings |
| `ai_model` | `deepseek-flash` | 生产库 settings |
| `price_in` | 1.0 ¥/百万 token | 未设置 → 用默认值 |
| `price_out` | 2.0 ¥/百万 token | 未设置 → 用默认值 |

核对：DeepSeek V4-Flash 官方价 $0.14/$0.28 每百万 token ≈ **¥1.0/¥2.0** —— **应用里的默认单价是准确的**，下面的测算可信。

### 1.2 单条成本公式

```
单条成本 = (S + I·B + 2·O·B) / (B × 10⁶)   元
  S = 系统提示词 token（每次请求固定）
  I = 单条输入 token
  O = 单条输出 token
  B = 每批条数
  （输出单价是输入的 2 倍）
```

两种输出规格（**这是成本差异最大的地方**）：

| 规格 | 适用 | S | I | O | 说明 |
|---|---|---:|---:|---:|---|
| **全量评分** | 视频 / 评论 | 1,500 | 110 | 110 | `SCORER_SKILL` 8 维 + `topic` + `reason`(20-40字) |
| **二值判定** | 弹幕 | 800 | 15 | 6 | 只回 `{key, drop:0/1}`，无理由生成 |

单条成本：

| 场景 | B=1（不批处理） | B=15 | B=50 |
|---|---:|---:|---:|
| 视频/评论 | ¥0.00183 | **¥0.00043** | — |
| 弹幕 | ¥0.000827 | — | **¥0.000043** |

> 批处理把系统提示词摊销掉，是最大的省钱杠杆（**4.2 倍**）。但注意：批处理上限受 `max_tokens=8192` 约束，全量评分批 15~30 已是极限。

### 1.3 三档场景测算

数据基础：视频抓取量来自生产库实测（10-08: 8,455 条 / 10-09: 6,305 条），取 **7,000 条/天**。
评论/弹幕量按每视频量级估算（B站单视频弹幕通常 3,000~8,000 条）。

| 场景 | 视频 | 评论 | 弹幕 | 合计/天 | **合计/月** |
|---|---:|---:|---:|---:|---:|
| **轻度**（20 视频/天，每视频 300 评论 + 3,000 弹幕） | ¥3.01 | ¥2.58 | ¥2.58 | ¥8.17 | **¥245** |
| **中度**（40 视频/天，每视频 500 评论 + 5,000 弹幕） | ¥3.01 | ¥8.60 | ¥8.60 | ¥20.2 | **¥606** |
| **重度**（40 视频，评论全量 2,000/视频 + 8,000 弹幕） | ¥3.01 | ¥34.4 | ¥13.8 | ¥51.2 | **¥1,536** |

**不做批处理**（每条一次请求）的中度场景：**¥2,200/月**。

### 1.4 结论

> **用户完全正确。三通道全开 AI 是 ¥245 ~ ¥1,536/月量级，重度 + 不批处理可到 ¥2,200/月。**
>
> 这不是「一杯咖啡」，这是**一年的软件订阅费**。v1 的 ¥1.52 是「功能没开」的账单，不能用来论证成本。

## 2. 决定性障碍不是成本，是**吞吐量**

成本还能靠批处理压，**吞吐量压不动**。

### 2.1 0.5B decoder 在 CPU 上的硬上限

| 来源 | 配置 | 单条延迟 |
|---|---|---:|
| Qwen3-0.6B 实测（CSDN 星图） | CPU + INT4 量化 | **1,200 ms** |
| Qwen2.5-0.5B 实测（llama.cpp） | CPU + Q5_K_M + prompt 只出 1 token + prefix cache | **300 ms** |

取乐观值 300ms → **吞吐上限 3.3 条/秒**；取保守值 1,200ms → **0.83 条/秒**。

> 该实测原文明确写：**「CPU 模式（量化 INT4）推理延迟升至 1200ms，不推荐」**「CPU 服务：仅用于调试，生产环境务必配 GPU」。

### 2.2 需求吞吐 vs 供给吞吐

| 场景 | 日处理量 | 24h 均摊需求 | 乐观供给(3.3/秒) | 保守供给(0.83/秒) |
|---|---:|---:|---|---|
| 轻度 | 73,000 条 | 0.85 条/秒 | ✅ 勉强（26% CPU） | ⚠️ **100% 满载 24 小时** |
| 中度 | 227,000 条 | 2.63 条/秒 | ⚠️ **80% CPU 全天** | ❌ **超载 3.2 倍** |
| 重度 | 407,000 条 | 4.71 条/秒 | ❌ **超载 1.4 倍** | ❌ **超载 5.7 倍** |

### 2.3 真正的杀手：突发

上面的「24h 均摊」已经很难看了，但**真实负载是突发的**：

- 用户打开一个视频 → **5,000 条弹幕要在弹幕加载前几秒内判完**
- 需要突发吞吐 **≈ 1,000 条/秒**
- 0.5B decoder 供给 **0.83 ~ 3.3 条/秒**
- **差距 300 ~ 1,200 倍**

> **结论：0.5B decoder 不是「贵不贵」的问题，是「根本跑不完」的问题。**
> 它连「中度场景的弹幕通道」都接不住，更别说视频 + 评论 + 弹幕三通道。

## 3. 「现成模型下载下来就能用」——实测数据说不行

### 3.1 Qwen3-0.6B 零样本实测（Ag News 四分类，英文，**简单任务**）

| 方案 | 准确率 | 推理 RPS (GPU) |
|---|---:|---:|
| **零样本 No-Think** | **78.98%** | 11.2 |
| 零样本 Think | 79.97% | 0.54 |
| SFT 微调 | 94.1% | 13.2 |
| Linear Head | 94.9% | 38.1 |
| BERT-base 微调 | 94.5% | **60.3** |

**三个致命的细分数据**：
1. **短文本（<50 词）零样本准确率掉到 69.1%**（No-Think）
2. 跨领域混淆严重（Business ↔ Sci/Tech 大量误判）
3. 含缩写/专有名词的句子易错

### 3.2 映射到我们的任务

| 维度 | Ag News 实测条件 | 我们的实际情况 | 影响 |
|---|---|---|---|
| 任务难度 | 4 分类 | **8 维打分**（0-10 连续 + 标签 + 生成） | 难得多 |
| 语言 | 英文 | **中文**（含网络黑话/谐音/缩写） | 难得多 |
| 文本长度 | 平均 280 token | **弹幕 5~20 字、评论 10~100 字** | 正好落在 **69.1%** 的最差区间 |
| 判据 | 主题分类 | 引战/低质/密度/情绪，**需要反讽、语境、立场理解** | 难得多 |
| 标注数据 | 零样本 | 零样本 | — |

> **零样本 0.6B 在我们这个任务上，实际表现会显著低于 69%。**
> 而「70% 准确率」在筛选场景里等于**每 3 条就错 1 条** —— 用户会直接弃用。

### 3.3 所以「现成模型」的真实处境

| 用法 | 可行？ | 原因 |
|---|---|---|
| 直接下载 Qwen3-0.6B 零样本用 | ❌ | 中文短文本 ≈ 60~70%，筛选场景不可接受 |
| 下载后自己微调 | ⚠️ 可行但选错了对象 | 见 §4 |
| 下载 encoder 微调 | ✅ **正解** | 见 §4 |

**关键洞察**：无论哪条路，**都绕不开「微调 + 标注数据」**。既然必须微调，就该微调**推理快 100 倍的 encoder**，而不是 0.5B decoder。

## 4. 修正后的结论：该做，但形态完全不同

### 4.1 选型对比

| 指标 | 0.5B decoder (Qwen3-0.6B) | **~100M encoder (RoBERTa/MacBERT)** |
|---|---|---|
| 磁盘 | 380 MB (Q4) / 480 MB (Q5) | **~100 MB** (int8 ONNX) |
| 运行时 RAM | 600 ~ 1,000 MB | ~200 ~ 300 MB |
| **CPU 吞吐** | **0.83 ~ 3.3 条/秒** | **200 ~ 1,500 条/秒** ⚠️估算 |
| 相对速度 | 1× | **60 ~ 450×** |
| 输出形态 | 自由文本，需解析 | **logits，天然适配打分** |
| 微调成本 | LoRA，需 ~1 小时 GPU | 训练快，CPU 也能训 |
| 零样本可用性 | ~69%（短文本） | 不适用（必须微调） |
| 突发 1,000 条/秒 | ❌ 差 300~1,200 倍 | ✅ 可满足 |

> ⚠️ encoder 吞吐是**量级估算**，需本地实测确认（弱机可能只有 200 条/秒，仍比 decoder 快 60 倍）。

### 4.2 正解不是「取代 API」，是**三级漏斗**

| 层 | 手段 | 吞吐 | 边际成本 | 拦截 |
|---|---|---|---|---|
| **L1** | 机械规则（现有） | 百万+/秒 | **0** | 明显垃圾：播放量/时长/去重/词表/黑名单 |
| **L2** | **本地 encoder** | 200~1,500/秒 | **0** | 语义层：引战/低质/标题党/无信息量 |
| **L3** | API | ~0.5/秒 | ¥ | 只剩**精判 + `topic` + `reason` 生成** |

**效果**：L3 的输入量被 L1+L2 砍掉 **95%+**
→ API 成本从 **¥245~1,536/月** 降到 **¥15~75/月**
→ 同时保住 AI 级筛选质量

**这才是「既要 AI 级质量，又不花大钱」的正解**，而不是「用 0.5B 换掉 API」。

### 4.3 三条链路的最终处置

| 链路 | 处置 | 理由 |
|---|---|---|
| **信息筛选** | ✅ **上 encoder（L2）** | 真·语义分类问题，唯一有增益空间；机械侧词表穷举、无上下文 |
| **评论筛选** | ⚠️ **看情况** | 现有身份关联（`keep()` 查表 3~45ms）已覆盖主要需求；若要做「评论内容语义筛选」才需要 encoder，且必须走**壳端异步**，不能进渲染进程 |
| **弹幕筛选** | ⚠️ **encoder 可行，decoder 不可行** | 现有 `processAsync` 已经是「异步问壳 + 超时兜底」架构，壳端挂 encoder 架构上通；**但 decoder 的 300~1,200ms/条绝对不行** |

### 4.4 明确不能做的事

| ❌ | 原因 |
|---|---|
| 用 0.5B decoder 做三通道全量筛选 | 吞吐差 300~1,200 倍，**跑不完** |
| 零样本直接用 | 中文短文本 ≈ 60~70%，筛选场景不可接受 |
| 在渲染进程内加载模型 | 用户脚本必须同步亚毫秒；加载就要 50~500ms |
| 不做 L1 粗筛直接上模型 | 白白浪费 70% 的算力在明显垃圾上 |

## 5. 落地路线（关键路径已明确）

### 第 0 步 —— **必须最先做，且零额外成本**

**把 AI 评分打开跑起来，把 `SCORER_SKILL` 的输出落库。**

- 现状：`items` 表 **24,511 条**，`score_json` **全为空** → **零标注数据**
- 而 §3 已证明：无论 decoder 还是 encoder，**都必须微调**，而微调必须有标注
- **L2 的训练标签，只能来自 L3** —— 这是整条路线的**唯一数据来源**
- 成本：按实测单价，默认档跑满一年约 **¥13**

> 这一步不做，后面全部无法启动。**这是整条路线的关键路径。**

### 第 1 步 —— 用 API 评分数据反查机械规则的漏网与误伤（免费）

- 哪些 `flame≥8` 的内容不含任何 `FLAME_SLURS` 词？→ 补词表
- 哪些被 `CLICKBAIT_RE` 命中的实际 `spam≤3`？→ 修正则
- 这一步可能吃掉大部分「机械筛选太弱」的痛点，**零模型成本**

### 第 2 步 —— 蒸馏训练中文 encoder

- 数据：第 0 步积累的 API 评分（目标 ≥1 万条）
- 模型：中文 RoBERTa / MacBERT-base，int8 ONNX
- 部署：壳端（127.0.0.1）异步，复用现有 `/api/bili/flags` 那套「异步 + 超时兜底」模式
- 只接**分类头**（`flame`/`spam`/`density`/`emo`/`facts`），`topic`/`reason` 仍留 API

### 第 3 步 —— 观察 L3 调用量下降比例，再决定是否继续加码

## 7. 一句话总结（修正版）

> **v1 错了，用户是对的：三通道全开 AI 确实是 ¥245~1,536/月，不是 ¥1.52。**
>
> **但 0.5B decoder 接不住这个活**——CPU 上 0.83~3.3 条/秒，而弹幕突发需要 ~1,000 条/秒，**差 300~1,200 倍**。而且零样本在中文短文本上只有 60~70%，等于每 3 条错 1 条。
>
> **正解是三级漏斗**：机械规则（免费）→ **~100MB 中文 encoder**（免费，200~1,500 条/秒）→ API（只剩精判 + reason，¥15~75/月）。
>
> **而现在唯一该做的事，是把 AI 评分跑起来攒标注数据**——因为 encoder 微调的标签只能来自 API，这是整条路线的关键路径，且一年只花 ¥13。
