## 1. 怎么制作 fastText

### 1.1 数据格式：一行一条，`__label__标签 文本`

```
__label__yy 赢麻了
__label__yy 又是魂游
__label__ok 这游戏画面真不错
__label__ok 请问这个配置能跑吗
```

就这么多。**没有 header，没有 JSON，没有 train/val 划分的强制要求**（可以自己切）。

### 1.2 训练代码：一行

```python
import fasttext

model = fasttext.train_supervised(
    input="train.txt",
    lr=0.5,
    epoch=50,
    wordNgrams=2,      # ★ 二元词组特征（抓「又是X」这类句式）
    minn=2, maxn=4,    # ★★ 字符级 n-gram（中文必须开，否则整句被当成一个词）
    dim=100,
    loss="softmax",
    bucket=20000,      # ★★★ 决定模型体积，见 1.4 的坑
    verbose=0,
)
model.save_model("model_yy.bin")
```

### 1.3 本机实测（238 条样本）

```
样本总数 : 238  (阴阳怪气 153 / 正常 85)
训练耗时 : 0.15 秒
模型体积 : 7.73 MB
```

**0.15 秒。** 没有 GPU、没有调参、没有梯度下降的等待。这就是 fastText 最爽的地方——**你可以迭代到天亮**。

### 1.4 ★ 必须知道的坑：`bucket` 决定模型体积

模型体积 ≈ `(词表 + bucket) × dim × 4 字节`

| bucket | dim | 模型体积 |
|---:|---:|---:|
| 20,000 | 100 | **7.73 MB**（本 demo 用的） |
| 200,000 | 100 | ~80 MB（我第一版误设，实测 76.39 MB） |
| **2,000,000**（fastText 默认） | 100 | **~800 MB** ⚠️ |

**第一次训练出来 76 MB 是正常的**——默认 `bucket` 是 200 万，直接给你一个 800 MB 的模型。
对本任务（词表几百个、标签 2~10 个）**`bucket=20000` 完全够用**。

### 1.5 中文的三个要点

| 要点 | 说明 |
|---|---|
| **必须开 `minn/maxn`** | 中文没有空格，整句会被当成**一个 token**。靠字符级 n-gram（2~4 字）才能切出特征 |
| **可以跳过分词** | 字符级 n-gram 自带分词能力。实测未分词效果已经很好，省掉 jieba 依赖 |
| **不要用官方预训练词向量** | `cc.zh.300.bin` 有 **6.7 GB**，为了分类任务没必要 |

### 1.6 样本量要多少

| 目标 | 建议 |
|---|---|
| 先跑通、看效果 | **200~500 条**（本 demo 238 条就能到 83.8% 总体） |
| 上生产 | **3,000~10,000 条**（类别均衡，每类 ≥500） |
| 覆盖长尾表达 | 持续从线上 badcase 补 |

**注意**：本 demo 的 238 条是我手工编的，**只用来验证机制，不能直接上生产**。

## 2. 怎么使用

### 2.1 加载与预测

```python
import fasttext

model = fasttext.load_model("model_yy.bin")

labels, probs = model.predict("又是魂游", k=2)
# labels = ('__label__yy',)   probs = array([1.0000001], dtype=float32)
```

`predict` 支持**批量**（传 list 比逐条快，也省 Python 开销）：

```python
model.predict(["赢麻了", "这游戏真不错", "又是魂游"])
```

### 2.2 接进产品的三种位置

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 壳端进程内** | `import fasttext` 直接在 `app.py` 里加载 | ✅ **推荐**。零 IPC 开销，最快 |
| **B. 壳端 HTTP 端点** | 起一个 `/api/filter` 端点，插件异步问壳 | ✅ 评论/弹幕链路适用（复用现有 `processAsync` 模式） |
| **C. 渲染进程内** | 塞进 user.js | ❌ 需要 JS 版 fastText，且模型文件要注入页面，不推荐 |

### 2.3 阈值与置信度（关键工程点）

```python
labels, probs = model.predict(text)
conf = probs[0]

if conf < 0.70:
    # 低置信 → 交给 encoder 或 API 复核（三级漏斗的 L2c/L3）
    pass
```

**本 demo 实测的置信度分布很有价值**：
- 标记词型：「赢麻了」1.000、「典中典」1.000 —— **极高置信**
- 反讽型（判错的）：「这游戏优化真好，我4080都掉帧」0.948 —— **高置信地判错** ⚠️
- 字面用法（判错的）：「这个月业绩赢麻了」0.587 —— **置信度偏低**

→ **结论：低置信可以当"复核信号"，但挡不住"高置信地判错"。** 不能只靠阈值兜底。

## 4. 为什么？看 n-gram 特征就全明白了

fastText **不理解句子**，它把字符串切成 n-gram，求平均，然后线性分类。下面是本机实际喂给模型的特征：

### 「赢麻了」 vs 「今天比赛赢麻了，太爽了」

```
「赢麻了」
   特征: 赢麻了  <赢  <赢麻  <赢麻了  赢麻  赢麻了  赢麻了>  麻了  麻了>  了>

「今天比赛赢麻了，太爽了」
   特征: <今  <今天  <今天比  今天  今天比  今天比赛  天比  天比赛  天比赛赢
        比赛  比赛赢  比赛赢麻  赛赢  赛赢麻  赛赢麻了  赢麻  赢麻了  赢麻了，
        麻了  麻了，  麻了，太  了，  了，太  了，太爽  ，太  ，太爽  ，太爽了
        太爽  太爽了  太爽了>  爽了  爽了>  了>

   → 共享特征: 赢麻了  赢麻  赢麻了  麻了  了>   (5/10)
```

**「赢麻了」这个短语的特征，在长句里原封不动地出现了 5 个。**
fastText 一看：这不是我训练时标记为「阴阳怪气」的那组特征吗？→ 判阴阳。

它**根本不知道**后面跟着「太爽了」，也不知道这是体育比赛。

### 「又是魂游」 vs 「这游戏是魂游，我挺喜欢的」

```
「又是魂游」
   特征: 又是魂游  <又  <又是  <又是魂  又是  又是魂  又是魂游  是魂  是魂游  是魂游>  魂游  魂游>  游>

「这游戏是魂游，我挺喜欢的」
   特征: ... 戏是魂  戏是魂游  是魂  是魂游  是魂游，  魂游  魂游， ...
   → 共享特征: 是魂  是魂游  魂游   (3/13)
```

这里共享特征只有 3/13，而且**不含「又是」**——所以模型判对了「正常」。
**如果长句里也出现「又是」，它一样会判错。**

> **一句话总结机制**：fastText 的判定 = 「这句话里出现了多少训练时见过的高权重 n-gram」。
> 它没有词序、没有句法、没有上下文、没有事实核查。

## 5. 能力边界：阴阳怪气分四类，它只吃得下两类

| 类型 | 例子 | fastText | 原因 |
|---|---|---|---|
| **A 词汇标记型** | 赢麻了、典、急了、笑死、孝、啊对对对 | ✅ **100%** | 有固定标记词 → n-gram 命中 |
| **B 句式标记型** | 又是X、不愧是X、只能说X | ✅ **100%** | `wordNgrams=2` 能学到「又是」+「X」的组合 |
| **D 表情符号型** | 😅 🥰 6 典中典 | ✅ **100%** | 符号本身就是特征 |
| **C 语用反讽型** | 「优化真好，我4080都掉帧」 | ❌ **40%** | **无标记词**，靠事实反差，需要世界知识 |
| **E 字面用法** | 「今天比赛赢麻了」 | ❌ **40%** | **同一串字符**，模型无从区分 |

**好消息**：B站/游戏社区的阴阳怪气，**绝大多数属于 A/B/D**（「赢麻了」「典」「急了」「又是魂游」全是标记型）。这正是 fastText 的舒适区。

**坏消息**：C 和 E 是**结构性盲区**，不是数据量能解决的——喂再多数据，只要「赢麻了」两个字在真心话和阴阳话里长得一模一样，模型就没法区分。

| 方案 | 吞吐 | 相对倍数 |

## 7. 一个必须提前知道的部署坑

**fastText 在 Windows 上没有现成 wheel。**

- PyPI 上的 `fasttext` / `fasttext-wheel` **都只有源码包**，装的时候要 **MSVC C++ 编译环境**
- 我本机（Python 3.13）**装失败**：`Microsoft Visual C++ 14.0 or greater is required`
- 最后是**降级到 Python 3.11 + 用社区预编译 wheel** 才跑起来的

**对本产品的含义**：
- 如果要把 fastText 打进 PyInstaller 的 exe，**构建机上必须有 MSVC 编译工具链**，或者
- **锁定 Python 3.10/3.11** 并使用社区 wheel（本 demo 走的这条路）
- 这是个**需要在打包流水线里提前验证**的事项，不是"装上就能用"

（本次验证环境：免安装 Python 3.11.9 + `fasttext-0.9.2-cp311-cp311-win_amd64.whl` + numpy 1.26.4，全部装在 `_py311/` 里，**未污染系统环境**。）

## 8. 落到我们的场景：该怎么用

| 链路 | fastText 角色 | 预期效果 |
|---|---|---|
| **弹幕筛选** | ✅✅ **主力** | 超短文本（5~20 字）+ 强标记词（「典」「急了」「又是X」）+ 63,000 条/秒 → **教科书级适用** |
| **评论筛选** | ✅ **主力** | 短文本 + 标记词覆盖大部分；走壳端异步 |
| **信息筛选（标题）** | ✅ **粗筛** | 标题党/震惊党是标记词型；但 `density`/`interest` 这类需要 encoder 或 API |

**三级漏斗里的位置**：

```
L1 机械规则（词表/正则，免费）
    ↓
L2a fastText（7.73 MB，63,000 条/秒，抓标记词型阴阳怪气）   ← 本 demo 验证的就是这层
    ↓  低置信 或 长文本
L2b/L2c 中文 encoder（抓语用反讽，需上下文）
    ↓  精判
L3 API（topic + reason 生成）
```

**fastText 单独用不够**（反讽 40%），**但它能把 80%+ 的标记词型内容零成本拦掉**，让 encoder 和 API 只处理剩下的硬骨头。

## 9. 一句话总结

> **fastText 极好做（238 条样本 / 0.15 秒 / 7.73 MB）、极快（63,557 条/秒，比 0.5B 模型快 19,000~77,000 倍）。**
>
> **对「赢麻了」「又是魂游」这类标记词型阴阳怪气，它判得又准又自信（置信度 1.000）。**
>
> **但它是纯模式匹配**：同一个「赢麻了」，真心话也被判成阴阳（0.877）；「优化真好，我4080都掉帧」这种靠反差的，它完全看不出来（40%）。
>
> **所以正确定位是 L2a 粗筛**——吃掉 80% 标记词型的量，把反讽和长文本留给 encoder。
>
> **样本量是关键**：本 demo 的 238 条是我手工编的，只验证机制。真正上线需要 3,000~10,000 条，**而这些标签只能从 API 评分里来**——又回到了第 0 步。
